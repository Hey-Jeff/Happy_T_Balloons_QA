# QA02 — conectar la dirección publicada a GitHub Actions

**URL proporcionada:** `http://13.184.33.122` (HTTP, sin TLS).

## Primer intento (sin contraseñas)

1. Descomprime el ZIP y sube **el contenido de** `QA02_Automatizacion_HappyTimes/` a la raíz de un repositorio GitHub privado. No subas la carpeta contenedora completa.
2. Comprueba que `.github/workflows/qa02-manual.yml` está en la rama principal.
3. Ve a **Actions → QA02 Happy Times Balloons - ejecución manual → Run workflow** y selecciona `conexion`.
4. GitHub ejecutará `npm run qa:validate`, pruebas unitarias y `scripts/check-env.mjs`. La URL predeterminada ya es `http://13.184.33.122`.
5. Si el sitio responde con un código de acceso válido, prueba `publicos` (5 borradores anónimos; pueden fallar si los selectores no corresponden a la interfaz).
6. Abre la ejecución en Actions → **Summary** y descarga los artifacts si existen.

### Actualizar la URL

En GitHub: **Settings → Secrets and variables → Actions → Variables → New repository variable**. Nombre: `QA_BASE_URL`. Valor: la URL completa del entorno de QA. Si falta, el workflow usará `http://13.184.33.122`.

### Si falla `conexion`

- Si el log muestra **Connection refused**, revisa que el servidor esté activo y que haya un servicio escuchando en el puerto 80.
- Si muestra **timeout**, revisa reglas de entrada (security group/firewall), balanceador, reglas de red y restricciones al runner de GitHub.
- Si hay redirección a HTTPS, usa directamente la URL HTTPS en la variable `QA_BASE_URL`.
- Si devuelve 401/403, revisa autorización de red o controles de acceso antes de habilitar automatización.
- Una comprobación fallida desde este entorno no prueba por sí sola que el sitio esté caído: valida desde GitHub y un navegador real.

### Seguridad: autenticación

No configures ni envíes contraseñas mientras utilices HTTP público. El workflow bloquea casos que requieren autenticación mediante HTTP y el helper también impide escribir contraseñas si la página real no usa HTTPS.

Cuando publiques el sitio en un nombre de dominio con certificado HTTPS válido, cambia `QA_BASE_URL` a esa URL y entonces podrás configurar los secrets `QA_ADMIN_EMAIL`, `QA_ADMIN_PASSWORD`, `QA_CLIENT_EMAIL`, `QA_CLIENT_PASSWORD` y `QA_INVALID_PASSWORD`. Usa cuentas de prueba dedicadas. **Nunca** credenciales reales. 

La aplicación podría exponer productos, clientes, pedidos y pagos: este workflow fuerza `QA_ALLOW_MUTATIONS=false`. Las pruebas que requieren cambios de datos deben ejecutarse únicamente en un entorno QA aislado y con datos de prueba controlados.

### Modos

| Modo | Qué hace |
|---|---|
| `validar` | Verifica 105 casos y pruebas unitarias, sin conectarse al sitio. |
| `conexion` | Verifica disponibilidad de la URL desde el runner. |
| `publicos` | Ejecuta los 5 borradores anónimos: CAT-001, CAT-002, CAT-004, CAT-006 y CLI-006. |
| `borradores` | Intenta los 10 borradores; en HTTP se bloquea por incluir autenticación. |
| `modulo` | Ejecuta el módulo seleccionado; si incluye login en HTTP, bloquea. |
| `caso` | Ejecuta un caso concreto; si incluye login en HTTP, bloquea. |

**Estado real:** 105 casos importados, 10 borradores sin verificar, 87 pendientes de implementación y 8 excluidos/no aplicables. No hay 105 pruebas de navegador listas ni ejecuciones funcionales verificadas.
